# RFC-023 — One file to install, Pull + Up to update

| | |
|---|---|
| **Status** | Proposed 2026-11-26, for the owner's review |
| **Date** | 2026-11-26 |
| **Depends on** | The 1.15 stack (no Kong, the webapp serves `/rest/v1` and the files itself); the migration runner in the image (`migrate.sh`, `webapp-entrypoint.sh`); the published image `ghcr.io/svenger87/kinboard` |
| **Discussion** | #539, #282, #106 |

## 1. Why

Every update question so far comes from the same gap: the git folder on one
side, the containers that actually run on the other. Updating one does not
update the other, and nothing says so.

- **#106 (2026-08-05).** `docker compose pull && docker compose up -d` left an
  install on 1.5.0 for several upgrades. The published 1.6.0 image was on
  disk (`sha256:66250731c60c`), but compose built the webapp from the 1.5.0
  checkout instead, because the image was defined in an overlay that a bare
  `docker compose` does not read. Since 1.15 the base file runs the image
  itself (`webapp/docker/docker-compose.image.yml:1-6`).
- **#282 (2026-11-19).** A Windows/WSL household's autostart ran
  `git pull --ff-only && ./start.sh up`. Git said "Already up to date", the
  container list showed `kinboard-webapp` created "7 days ago", and Settings
  kept saying 1.15 while the changelog dialog showed 1.16. `start.sh up` did
  not pull the image then; #491 added that (`webapp/docker/start.sh:257-269`).
- **Discussion #539 (2026-11-26).** An OpenMediaVault user installs everything
  through OMV's Compose plugin. `git pull` says up to date, `./start.sh up` and
  `restart` keep 1.16. The git folder and the OMV-managed containers are two
  different installs. He asked for "directions for using Docker Compose" and
  wrote "I don't typically do things in command line".

Each of the three did what the instructions said, and each time the containers
came from somewhere the instructions didn't touch. The fix is not better
instructions. It is to remove the second place: one compose file, pasted into
whatever runs it, updated by that tool's Pull and Up.

Today three things tie a running stack to a terminal and a git checkout:

1. **Secrets in `webapp/docker/.env`, generated by `setup.sh`.**
   - `POSTGRES_PASSWORD`, `JWT_SECRET`, `CRON_SECRET`, `PRESENCE_SENSOR_TOKEN`
     and `DIUN_WEBHOOK_SECRET` are random hex (`setup.sh:221-236`).
   - `ANON_KEY` and `SERVICE_ROLE_KEY` are HS256 JWTs signed with
     `JWT_SECRET` (`setup.sh:242-283`).
   - The VAPID keys need Node.js on the host: `npx web-push
     generate-vapid-keys` (`setup.sh:289-310`). Without Node, push stays off
     and setup says so at the end (`setup.sh:526-535`).
   - The compose file reads every one of these from `.env` by interpolation
     (`docker-compose.yml:60-61, 126, 146, 150, 279-280, 288, 317, 328-330,
     342, 368`). Without `.env` they are empty and the stack doesn't start.
2. **Files from the repo, bind-mounted:**
   - `./init.sql` into the database's `docker-entrypoint-initdb.d`
     (`docker-compose.yml:77`);
   - `./go2rtc.yaml` into go2rtc (`docker-compose.yml:400`).

   A compose file pasted into a UI has no `./init.sql` next to it.
3. **API keys asked for by `setup.sh` or written into `.env`.** OpenWeatherMap
   and the Google OAuth client exist only as environment variables (§4.4).

There is a fourth tie, and it decides the design: **the compose file changes
with releases.** Since 2026-08-01, 20 commits changed
`webapp/docker/docker-compose.yml`. Five of them added scheduled jobs, which
live as ofelia labels in that file:

- 2026-08-09: the Heute-Motor;
- 2026-10-02: school holidays;
- 2026-10-03: closing a task's day;
- 2026-10-16: Bring!;
- 2026-10-20: repeating events.

A git install gets them through `git pull`. A pasted file would never get them,
and nothing would say so: a job that doesn't exist doesn't fail. That is #106's
failure again, in a new place.

## 2. The rule: the image carries what changes, the file carries what the household chooses

Everything a release may change ships in the image: the migrations (already
there, `Dockerfile:247-248`), the base schema, the job schedule, the go2rtc
defaults and secret generation. The compose file holds only what a household
chooses: the port, the time zone, where the data lives and which channel it
follows. With that split, Pull + Up is a complete update.

**The second rule: an existing install changes nothing unless it opts in.**
Its `docker-compose.yml`, `.env`, `start.sh`, overlays and Diun self-update keep
working exactly as they do (§5).

## 3. Goals and non-goals

**Goals**

- One self-contained `compose.yml`, images only, that can be pasted into
  OpenMediaVault's Compose plugin, Portainer stacks, Unraid's Compose Manager,
  Dockge or CasaOS and started with no terminal, no git and no `.env`.
- Updating is Pull + Up in that UI, and nothing else.
- Every secret creates itself on first start. A value already in `.env` wins.
- Every API key can be set in Settings. `.env` is still honoured.
- `install.sh` produces the same file, so there is one way of running Kinboard.
- Existing installs: no change unless they opt in, and a written path for when
  they do.

**Non-goals**

- Automatic updates for one-file installs. Diun stays optional, and a
  published updater image is an open question (§11.3).
- Retiring `webapp/docker/docker-compose.yml`. It stays the file for git
  installs; when it retires is a later decision.
- A full backup that can be downloaded from Settings (§6.5 says why it is
  wanted; it gets its own RFC).
- An all-in-one image and listings in app stores (Unraid Community
  Applications, TrueNAS, CasaOS, Umbrel and others). They are
  [RFC-024](024-all-in-one-and-stores.md), which builds on this one.
- Running without Docker, or a Helm chart.

## 4. Design

### 4.1 Secrets that create themselves

**Where.** A volume of its own, `kinboard-config`, with a `secrets/`
directory. One file per secret:

| File | Used by | Today | Generated as |
|---|---|---|---|
| `postgres_password` | db (first start only), db-init, webapp (migrations, LISTEN) | `.env` | 32 random bytes, hex. URL-safe, as `setup.sh:217-220` requires for connection strings |
| `jwt_secret` | rest, webapp (family tokens, signed file URLs) | `.env` | 32 random bytes, hex |
| `db_uri` | rest | built by compose from `POSTGRES_PASSWORD` (`:146`) | derived from `postgres_password` on every start (the password URL-encoded) |
| `cron_secret` | the scheduler and the cron routes | `.env` | 32 random bytes, hex |
| `presence_sensor_token` | `/api/presence` | `.env` | 32 random bytes, hex |
| `vapid_public_key`, `vapid_private_key` | push | `.env`, needs Node on the host | a P-256 key pair from the image's own Node (the `web-push` library the server already uses for sending, `src/lib/push-sender.ts`) |

**Not stored: the anon and service-role keys.** Both are HS256 JWTs signed
with `jwt_secret` (`setup.sh:263-280`). The webapp mints them from
`JWT_SECRET` when `ANON_KEY` and `SERVICE_ROLE_KEY` are unset. It already mints
family tokens the same way (`src/lib/family-jwt.ts:67-90`). The payloads are
fixed (`{"role":"anon","iss":"kinboard"}` and the service role's equivalent),
so the anon key a page holds in `window.__ENV` stays the same across restarts.
They carry no `exp`. A derived key is exactly as secret as the key it is
derived from: anyone who holds `jwt_secret` can mint a service-role token
anyway, and the anon key ships in every page (`src/app/layout.tsx:81`). Storing
them would only add a second thing that can disagree with `jwt_secret` after a
rotation. The service-role key never leaves the server: `/rest/v1` refuses it
from outside (`src/lib/rest-proxy.ts:43-46`).

**Precedence, per secret: the `.env` value, then the file, then generate.**

1. A value in the environment (from an existing `.env`) wins. The init step
   writes it into the file, so every service reads one value.
2. Otherwise the file is kept as it is.
3. Otherwise the value is generated and written.

One exception: **`postgres_password`, when the file exists and `.env` holds a
different value, is a refusal.** The database took its password at its first
start and does not read it again. Neither value can be checked before the
database runs, and picking the wrong one locks the stack out of its own
database. The init step exits non-zero and names both sources, and nothing
starts. Every other secret can change at a restart (§6.4 lists what each change
costs). For those, the `.env` value wins, the replaced file is kept as
`<name>.previous-<UTC timestamp>`, and the init step logs a warning.

**The init step.** A one-shot service `init`, run from the **webapp image**
with `command: ["kinboard-init"]`. There is no new image: the webapp image
already has Node, `psql` and a root entrypoint (`Dockerfile:108, 249`). It
mounts `kinboard-config` read-write and the database volume read-only, and
runs in this order:

1. **Check where the data lives.** It refuses a filesystem PostgreSQL cannot
   use (`vfat`, `msdos`, `cifs`, `9p`, `drvfs`, `fuseblk`) and one that does
   not survive a reboot (`tmpfs`, `ramfs`). This is `start.sh`'s WSL check
   (`start.sh:148-206`) moved into the stack, so it protects every install,
   not just `start.sh` users. `vfat` is the case that matters: Unraid's
   Compose Manager keeps projects on the USB flash drive (§4.6).
2. **Fill in the secrets** by the precedence above. Each file is written to a
   temporary name and renamed into place, so an interrupted start leaves
   either the old file or the new one, never half of one.
3. **Guard the database password.** If `postgres_password` is missing but the
   database volume already holds a cluster (`PG_VERSION` exists), it refuses.
   A new password would not match the database. The log says to restore
   `secrets/postgres_password` from a backup, or to set `POSTGRES_PASSWORD`.
4. **Set ownership and modes** (§6.2) and read them back. If they did not
   stick (some network shares ignore `chmod`), it logs a warning naming the
   files.
5. **Rewrite `db_uri`** from `postgres_password`.
6. **Log one line per secret**: `kept`, `generated`, `taken from .env`, or
   `replaced from .env (previous kept)`. It never logs values.

`db` waits for it with `condition: service_completed_successfully`, so a
failed init step stops the stack before anything starts.

**How each service reads the store:**

| Service | How | Verified |
|---|---|---|
| db | `POSTGRES_PASSWORD_FILE=/kinboard/secrets/postgres_password` | **Yes, by booting `supabase/postgres:15.14.1.159` with only `_FILE` set** (Appendix A). The image's entrypoint is docker-library's, with `file_env` (`docker-entrypoint.sh:10-25` in the image); it exports `POSTGRES_PASSWORD` before the init scripts run, and supabase's own `migrate.sh` reads that variable to set `supabase_admin`'s password. Setting both `POSTGRES_PASSWORD` and `_FILE` makes the container exit, so `compose.yml` must never pass both |
| rest | `PGRST_JWT_SECRET=@/kinboard/secrets/jwt_secret`, `PGRST_DB_URI=@/kinboard/secrets/db_uri` | **Yes**, PostgREST v14.16 (Appendix A). The docs describe `@filename` for both settings: https://docs.postgrest.org/en/v14/references/configuration.html (`jwt-secret`, `db-uri`). A trailing newline in the file did not break JWT verification |
| db-init | reads the file and passes the password as a psql variable, `ALTER USER authenticator WITH PASSWORD :'pw'` | Design. Today the password is pasted into the SQL by compose interpolation (`docker-compose.yml:126`), which breaks on a quote in a hand-set password |
| webapp | `webapp-entrypoint.sh` exports any unset variable from its file before it starts the server; then mints the anon and service-role keys if they are still unset | Design. App code keeps reading `process.env` as today (`src/lib/family-jwt.ts:43`, `src/lib/supabase/server.ts:53`, `src/lib/push-sender.ts:66-68`, `src/app/api/presence/route.ts:59`) |
| scheduler | reads `cron_secret` from the same place (§4.5) | Design |

The entrypoint's exports reach only the server process. Anything started with
`docker exec` sees the container's configured environment, not the exports.
Ofelia's jobs run that way and authenticate with `$CRON_SECRET` from that
environment (`Dockerfile:111-195`). The in-image scheduler (§4.5) avoids the
problem. If ofelia stays, the job scripts must fall back to reading the file.

### 4.2 The base schema: `init.sql`

`init.sql` is not a bootstrap of roles. It is the original core schema:

- 26 tables, plus the functions, triggers and indexes;
- the `pg_cron` extension (`init.sql:5-6`);
- 21 `ALTER PUBLICATION supabase_realtime ADD TABLE` statements
  (`init.sql:737-757`);
- a loop that hands ownership of everything to `postgres` (`init.sql:764`ff).

Migration 001 assumes it is there: its first statement alters `public.calendars`
(`migrations/001_base.sql:4`). Today the db container runs it once, as
`supabase_admin`, from a bind mount of the repo file (`docker-compose.yml:66-77`).

Three ways to drop the repo file:

| Option | For | Against |
|---|---|---|
| **a. Migration `000`**, run by `migrate.sh` | One runner, one history | **Fails on every existing database.** The runner has no row for 000, so it runs it, and `init.sql` has bare `CREATE TRIGGER` (`init.sql:317-341`) and `ALTER PUBLICATION … ADD TABLE`, both of which error when the object exists. Its `CREATE OR REPLACE FUNCTION`s are an old snapshot: run first, they would replace newer bodies that later migrations wrote, and those migrations would not run again, because their checksums are unchanged (`migrate.sh:84-96`). It also needs a superuser (`pg_cron`, the publication, the ownership loop), and the runner connects as `postgres`, which is not one (`migrate.sh:43`, `docker-compose.yml:104-106`). Making it work means a baseline mark for existing databases, a superuser connection and a rule that the file may never change |
| **b. A Kinboard database image** with `init.sql` baked in | Same mechanism as today | A second image to build, publish and keep up with every `supabase/postgres` security release. Not justified for one file |
| **c. The webapp image carries `init.sql`; `db-init` applies it** | No effect on existing databases. Same SQL, same user, same point in the order for everything that depends on it. No new image | `db-init` changes image |

**Decision: c.** The Dockerfile copies `init.sql` into the image, at
`/app/initdb/init.sql`. `db-init` runs from the webapp image
(`command: ["kinboard-db-init"]`). After it aligns `authenticator`'s password:

- It applies `init.sql` as `supabase_admin` **only when `public.families` does
  not exist**, with `--single-transaction`, so that a failed run leaves nothing
  behind that the check would mistake for a finished schema. That
  `CREATE EXTENSION pg_cron` and the publication changes run inside one
  transaction is to be verified in the PR.
- On an existing database the check is false and nothing runs.
- On a fresh one, the same file runs as the same user it runs as today. It runs
  after supabase's own init has created `authenticator`, which `db-init`
  already waits for (`docker-compose.yml:116-124`), and before `rest` and
  `webapp` start, which wait for `db-init` (`:143-144, 263-264`).

`webapp/docker/init.sql` stays where it is. The legacy compose file keeps
bind-mounting it, so one file has two readers. A test asserts that the copy in
the image is byte-for-byte the repo file.

### 4.3 go2rtc

The shipped `go2rtc.yaml` holds five example streams for Hikvision and Amcrest
cameras, filled from `CAMERA_*` variables (`go2rtc.yaml:16-29`). It also holds
the WebRTC candidates (`:31-35`). A camera added in Kinboard's settings needs
no entry there: the app passes the URL to go2rtc as `?src=`
(`src/lib/go2rtc.ts:93, 100`; wiki `Cameras.md:45`), and never writes streams
into go2rtc.

`compose.yml` drops the file and passes an inline config:

```yaml
go2rtc:
  image: alexxit/go2rtc:1.9.14
  command: ["go2rtc", "-config", "{webrtc: {candidates: ['$${WEBRTC_LAN_IP:}:8555', 'stun:8555']}}"]
  environment:
    WEBRTC_LAN_IP: ${WEBRTC_LAN_IP:-}
```

The `$$` stops compose from interpolating, so go2rtc does it, with its own
`${VAR:default}` syntax (https://github.com/AlexxIT/go2rtc/blob/master/internal/app/README.md).

- **Verified:** go2rtc 1.9.14 starts with only an inline config and listens on
  1984, 8554 and 8555.
- **Not verified:** whether the candidate list is right. Its `/api/config`
  answers `410 Gone` when there is no config file, so it can't be read back.
  That goes into rehearsal A.
- **Consequence:** `PUT /api/streams` answers 400, because go2rtc writes added
  streams back to its first config file
  (https://raw.githubusercontent.com/AlexxIT/go2rtc/v1.9.15/internal/streams/api.go).
  Kinboard never calls it.

The named streams `hikvision` and `amcrest` (still mapped to their `_wan`
twins in `src/app/api/cameras/webrtc/route.ts:47-48`) stay a git-install
feature. A one-file install with such a camera adds it in Settings by URL. A
household that wants go2rtc's own named streams mounts a file, as today; the
Compose UIs page shows how.

### 4.4 API keys in Settings

Where every credential lives today. Most are already per family in Settings,
in `integration_secrets`, which is readable by the service role only
(`migrations/020_integration_secrets.sql:9-28`,
`src/lib/integration-secrets.ts:11-42`):

| Credential | Today | Proposal |
|---|---|---|
| Home Assistant URL and token | Settings | — |
| Immich URL and key | Settings. `IMMICH_API_URL`/`IMMICH_API_KEY` are passed in compose (`:310-311`) and asked for by `setup.sh --advanced`, but nothing in `webapp/src` reads them | Leave out of `compose.yml`; mark as unused in `.env.example` |
| Unsplash | Settings | — |
| Bring! | Settings (tokens). `BRING_EMAIL`/`BRING_PASSWORD` in `.env.example:124-125` are read by nothing | As Immich |
| CalDAV | Settings, per calendar (`src/lib/caldav-credentials.ts:28-60`) | — |
| Cameras | Settings, passwords as secrets (`integration-secrets.ts:38-41`). `CAMERA_*`, `HIKVISION_HOST` and `AMCREST_HOST` feed only go2rtc's example streams | Not in `compose.yml` (§4.3) |
| **OpenWeatherMap key** | **Environment only** (`src/lib/weather-provider.ts:38-40`). Settings → Weather only says whether it is set (`settings/weather/page.tsx:145-152`) | **Settings → Weather**, stored as a family secret |
| **Google OAuth client ID and secret** | **Environment only** (`src/lib/google-calendar-auth.ts:19-20` and the `api/google/*` routes). Settings → Google Calendar shows a hint | **Settings → Google Calendar**, stored as a family secret. The redirect URI it shows today stays |
| **Presence sensor token** | **Environment only** (`src/app/api/presence/route.ts:59-65`). The household reads it from `.env` | **Settings → Presence sensor**: shown behind the settings PIN, with a "new token" button. Generated by the init step until one is set |
| SMTP, `JWT_EXPIRY` | Read by nothing (`.env.example:58, 93-97`) | Mark as unused |
| Photon, OpenHolidays switch, image search switch, rate limit, demo code | Install-wide knobs in the environment, no keys | Stay in the environment. Not in `compose.yml` by default; the docs show how to add one |

**Precedence for keys: Settings, then `.env`.** The Settings value is the more
specific and the later choice, and a household without a terminal can't change
`.env`. An install with a key in `.env` keeps working without touching
Settings. Settings shows "set on the server" and allows an override. This
follows `getMergedSetting` (`integration-secrets.ts:288-302`).

**Per family, not per install.** Immich, Unsplash and Home Assistant already
live per family, and the plumbing exists. An install-wide store, such as
`instance_settings`, which is service-role only (`065_instance_settings.sql:13-30`),
would raise the question of which family's settings PIN may change a key that
every family uses. Almost every install has one family, so per family costs
nothing. Open question §11.4.

As today, secrets in the database are stored as plain text, readable only by
the service role (wiki `Security-and-Threat-Model.md:41`). This RFC does not
change that.

### 4.5 The scheduler moves into the image

The 18 jobs are ofelia labels on the webapp container
(`docker-compose.yml:193-259`). Ofelia needs the Docker socket
(`docker-compose.yml:366`). In the stable 0.3 series it reads labels only when
it starts (https://github.com/mcuadros/ofelia/blob/master/docs/jobs.md, "real
time labels reading is not supported yet"), which is why `start.sh` and the
self-update recreate it after the webapp (`start.sh:208-230`). A pasted file
freezes the job list on the day it was pasted (§1).

**Proposal: for `compose.yml`, the webapp schedules its own jobs.**

- **The schedule.** The job list moves into the image as a module
  (`lib/schedule/jobs.ts`: name, schedule, route).
- **The runner.** When `KINBOARD_SCHEDULER=internal` is set, a runner started
  from Next's `instrumentation.ts` calls the same `/api/cron/*` routes over
  localhost with `CRON_SECRET`, as ofelia's scripts do. The cron routes don't
  change.
- **One job at a time.** Each job has a running flag, as ofelia's
  `no-overlap` does.
- **What it removes:** the socket from the default stack (§6.6), the labels and
  the recreate dance.
- **Off by default.** The variable is unset in the legacy file, so a git
  install keeps ofelia, and no install runs its jobs twice.

**Parity.** A CI test (in the `unit` project) compares the module with the
legacy file's labels: same names, same schedules. Adding a job to one and not
the other fails.

**Time zone, a finding to keep in mind.** The ofelia container gets no `TZ`
(`docker-compose.yml:367-368`), so its fixed-time jobs fire in UTC:
`todo-reminders` at 08:00 UTC, `birthday-reminders` at 07:00 UTC. This is
inferred: ofelia uses the container's local time, and the image sets no zone.
The internal runner must keep UTC for parity. Whether those should become the
household's local time is open question §11.1b.

### 4.6 The compose file

At the repository root as `compose.yml`. It is also attached to every release
as an asset, so `releases/latest/download/compose.yml` is a stable link and an
older version's file can still be found. Abridged:

```yaml
# Kinboard. Paste into your Compose UI and start it; update with Pull, then Up.
services:
  init:          # creates missing secrets, checks the data location; exits
    image: ghcr.io/svenger87/kinboard:${KINBOARD_TAG:-latest}
    command: ["kinboard-init"]
    restart: "no"
    environment:            # empty unless an existing .env provides them
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-}
      JWT_SECRET: ${JWT_SECRET:-}
      # … CRON_SECRET, PRESENCE_SENSOR_TOKEN, VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY
    volumes:
      - ${KINBOARD_CONFIG_DIR:-kinboard-config}:/kinboard
      - ${KINBOARD_DB_DIR:-kinboard-db}:/kinboard-db:ro

  db:
    image: supabase/postgres:15.14.1.159
    container_name: kinboard-db
    depends_on: { init: { condition: service_completed_successfully } }
    environment:
      POSTGRES_PASSWORD_FILE: /kinboard/secrets/postgres_password
      POSTGRES_HOST: /var/run/postgresql
      PGPORT: 5432
      POSTGRES_PORT: 5432
      PGDATABASE: postgres
      POSTGRES_DB: postgres
    volumes:
      - ${KINBOARD_DB_DIR:-kinboard-db}:/var/lib/postgresql/data
      - ${KINBOARD_CONFIG_DIR:-kinboard-config}:/kinboard:ro
    # no ports: nothing outside the stack needs the database

  db-init:       # aligns authenticator's password; applies init.sql to an empty database; exits
    image: ghcr.io/svenger87/kinboard:${KINBOARD_TAG:-latest}
    command: ["kinboard-db-init"]
    depends_on: { db: { condition: service_healthy } }
    volumes: [ "${KINBOARD_CONFIG_DIR:-kinboard-config}:/kinboard:ro" ]

  rest:
    image: postgrest/postgrest:v14.16
    environment:
      PGRST_DB_URI: "@/kinboard/secrets/db_uri"
      PGRST_JWT_SECRET: "@/kinboard/secrets/jwt_secret"
      PGRST_DB_SCHEMAS: public,graphql_public
      PGRST_DB_ANON_ROLE: anon

  webapp:
    image: ghcr.io/svenger87/kinboard:${KINBOARD_TAG:-latest}
    container_name: kinboard-webapp
    ports: [ "${WEBAPP_PORT:-3001}:3000" ]
    environment:
      TZ: ${TZ:-Europe/Berlin}
      SITE_URL: ${SITE_URL:-}
      KINBOARD_SCHEDULER: internal
      KINBOARD_COMPOSE_REVISION: "1"
      # … POSTGREST_URL, FILES_DIR, GO2RTC_URL, POSTGRES_HOST/PORT/USER/DB as today
    volumes:
      - ${KINBOARD_STORAGE_DIR:-kinboard-storage}:/var/lib/storage
      - ${KINBOARD_CONFIG_DIR:-kinboard-config}:/kinboard:ro

  go2rtc: { … §4.3 … }

volumes:
  kinboard-db:      { name: kinboard-db }
  kinboard-storage: { name: kinboard-storage }
  kinboard-config:  { name: kinboard-config }
```

The real file keeps today's healthchecks, `depends_on` conditions, log limits
(`docker-compose.yml:34-38`) and `restart: unless-stopped`.

**The variables. All optional:**

| Variable | Default | What for |
|---|---|---|
| `WEBAPP_PORT` | 3001 | the address families open |
| `TZ` | Europe/Berlin | as today (`docker-compose.yml:295`) |
| `KINBOARD_TAG` | latest | `next` for release candidates, or a version |
| `KINBOARD_DB_DIR`, `KINBOARD_STORAGE_DIR`, `KINBOARD_CONFIG_DIR` | named volumes | an absolute host folder, when the data should sit in a share |
| `SITE_URL` | empty | links handed to other apps; empty falls back to the request's address (`src/app/api/calendar/feed/route.ts:106-109`) |
| `WEBRTC_LAN_IP` | empty | cameras over WebRTC on the LAN |
| the six secrets | empty | only for an existing install that moves to this file (§5.2) |

**Where the data lives: named volumes by default.** The UIs disagree on what
`./data` means, and on two of them the answer loses data:

| UI | Compose | `${VAR:-default}` | `.env` / variables | `./data` lands in | Update |
|---|---|---|---|---|---|
| OMV 7 Compose plugin | CLI, ≥ 2.29.2 recommended | yes | per-file env plus `global.env`, passed as `--env-file` | the file's folder in the compose shared folder | Pull, then Up |
| Portainer CE, web editor | bundled v2 (2.26.1 in Portainer 2.20.3) | yes | "Environment variables" section, or `stack.env` | inside Portainer's own data path. Relative paths are a Business Edition, git-only feature (https://docs.portainer.io/advanced/relative-paths) | "Update the stack", with re-pull |
| Unraid Compose Manager | CLI v2.40.3 bundled | yes | an "ENV File" editor per project | **the USB flash drive**: projects default to `/boot/config/plugins/compose.manager/projects` | "Update Stack" (pull, then up) |
| Dockge | CLI | yes | `.env` per stack plus `global.env` | `/opt/stacks/<name>/data` | "Update" (pull, then up) |
| CasaOS, custom import | compose library 2.23.3, not the CLI | **apparently not**: on import an unset variable is reported as found, so `:-default` never applies (inferred from the code) | the app folder's `.env` | a temporary folder that is deleted (inferred) | no update path for custom imports (inferred) |

Sources, all read on 2026-11-26 (Appendix B lists the exact files):

- OMV: the plugin's `debian/control` and `compose.inc`.
- Portainer: docs.portainer.io stacks/add and edit, and the release notes.
- Unraid: `dcflachs/compose_plugin`, `default.cfg` and `compose.sh`.
- Dockge: `backend/stack.ts`.
- CasaOS: `CasaOS-AppManagement`, `compose_app.go` and `go.mod`.

Named volumes behave the same in all five. They don't depend on a working
directory, and Docker keeps them where it keeps everything else. A folder is
one variable away. Each volume has a fixed `name:`, so renaming the stack in a
UI doesn't start over with empty volumes.

Three separate variables, rather than one `DATA_DIR`, because a single variable
can't default to a named volume. The workaround, `${DATA_DIR:-kinboard}-db`,
works (tested with `docker compose config`), but produces folders called
`<DATA_DIR>-db` next to the chosen one. Three variables also map an existing
install exactly: `$DATA_DIR/db`, `$DATA_DIR/storage` and a new
`$DATA_DIR/config` (§5.2).

**What the file leaves out, compared with today's:**

- **No published database port.** `docker-compose.yml:55` publishes 5432 on
  every interface, which collides with any other PostgreSQL on a NAS and puts
  the database on the LAN.
- **No fixed subnet.** `:409` pins 10.200.0.0/24, so a second Docker project
  with the same subnet fails. Nothing in `webapp/src` reads `NETWORK_SUBNET`.
- **No Docker socket** (§4.5).
- **No ofelia labels, and no `CRON_SECRET` on the scheduler.** Ofelia's own
  copy is unused today: its jobs run inside the webapp
  (https://github.com/mcuadros/ofelia/blob/master/docs/jobs.md, `job-exec`).
- **No dead variables** (§4.4).

**Fixed container names** (`kinboard-db`, `kinboard-webapp`, …) stay. They
keep the documented commands (`docker exec kinboard-db …`) working. They also
make a second stack on the same host fail on the name, before it can open the
same data (§7).

**`KINBOARD_COMPOSE_REVISION`** says which version of `compose.yml` an install
runs. The image knows the lowest revision it needs. When the file is older,
Settings shows "This version wants a newer compose.yml" with a link to what
changed. The notice sits where Settings already shows "update available"
(`src/app/settings/page.tsx:1086-1095`). The revision goes up only when the file
itself must change: an image pin for the database, PostgREST or go2rtc, or a
new service. That has happened in one week since August
(2026-08-05/06, #121, #122, #125). The legacy file doesn't set the variable,
so git installs never see the notice.

### 4.7 Updating

**Pull, then Up**, in whatever runs the stack. That works because:

- the migrations run in the webapp's entrypoint
  (`webapp-entrypoint.sh:69-87`);
- the base schema applies only to an empty database (§4.2);
- the job list ships in the image (§4.5);
- the secrets persist in their volume (§4.1);
- `init` and `db-init` run again at every Up and find nothing to do.

The terminal equivalent is `docker compose pull && docker compose up -d`.

The one-shots show as "exited" in every UI. The Compose UIs page says that this
is what success looks like. `db-init` already does this today.

**Knowing that an update exists.** Settings already compares the running
version with GitHub's latest release, at most once every six hours
(`src/app/api/version-check/route.ts:4-6, 29-32`). That is the notice for a
one-file install. Diun can add a push notification without touching anything:
its notifiers (ntfy, Gotify, mail, a script;
https://github.com/crazy-max/diun/blob/master/docs/notif/script.md) need only
the read-only socket, or no socket with the file provider
(https://github.com/crazy-max/diun/blob/master/docs/providers/file.md). The
Compose UIs page gets that snippet.

### 4.8 The self-update

`kinboard-self-update.sh` is git-shaped from its first step:

- it runs `git fetch origin main` under `set -eu` (`:53, 425-427`);
- it runs `setup.sh`, which writes `.env` (`:469-474`);
- it reads `DATA_DIR` from `.env` for its backup (`:104`);
- it is started by a webhook container built locally from
  `Dockerfile.webhook` (`docker-compose.diun.yml:78-81`).

On an install with no git, it would log "git fetch origin main" and stop at the
failing command. There would be no backup and no update, and no message saying
why.

**For git installs, nothing changes.**

**For a directory without `.git`**, a guard at the top of the script says so
in plain words and exits 0: "this install has no git checkout; update it with
Pull and Up in your Compose UI, or `docker compose pull && docker compose up
-d`".

An **image-only mode** would also be easy to write: skip steps 1 and 2, take
the backup from the volumes the running containers mount (from
`docker inspect`, not `.env`), then pull and up. Nothing would need recreating
by hand, because the scheduler is in the image. But on a git-less install
nothing can run it: the webhook image is built from a file that only a git
checkout has. Publishing that image (`ghcr.io/svenger87/kinboard-updater`)
would be a new image. Open question §11.3. Until then, a one-file install gets
the notice, not an automatic update.

### 4.9 `install.sh`, `setup.sh`, `start.sh` and the overlays

**`install.sh` writes `compose.yml`.** It no longer clones the repo
(`install.sh:44`). It needs `docker` and `docker compose`, not `git`,
`openssl` or Node (`:21-27`). It:

1. downloads the release's `compose.yml` into `$KINBOARD_DIR` (default
   `./kinboard`);
2. writes a `.env` with only the optional variables, pointing the three
   directories at `./data/{db,storage,config}` there (in a terminal install a
   relative path is unambiguous);
3. runs `docker compose up -d`;
4. waits for `/api/health`, with a timeout;
5. prints the address.

It keeps its refusal to touch an existing directory (`:29-31`). The file is
byte-for-byte the one a UI user pastes, so there is one way of running
Kinboard. Contributors clone the repo, as they do today.

**The rest:**

| File | Stays for | Change |
|---|---|---|
| `setup.sh` | git installs on `docker-compose.yml` | Optional: generate VAPID keys with `docker run --rm <image> kinboard-init --vapid` instead of `npx` (`setup.sh:295`). That removes the Node requirement for git installs too |
| `start.sh` | git installs | Optional: `./start.sh adopt` performs §5.2's steps |
| `webapp/docker/docker-compose.yml` | git installs | None. A parity test (§4.5) keeps its jobs in line with the image |
| `docker-compose.traefik.yml` | both | Works as an overlay on `compose.yml` too: it names service `webapp`, network `kinboard` and container `kinboard-webapp`, all of which `compose.yml` keeps. The Compose UIs page shows its five labels pasted into the file instead |
| `docker-compose.build.yml`, `docker-compose.dev.yml` | contributors | None |
| `docker-compose.image.yml` | old `COMPOSE_FILES` lines | None |
| `docker-compose.diun.yml` | git installs with auto-update | None (§4.8) |
| `*.example` overlays (demo, watchtower, override) | as today | None |

**Unraid Community Applications and the other stores** are
[RFC-024](024-all-in-one-and-stores.md). A classic CA template describes one
container (https://ca.unraid.net/submit/help/repository-xml), which is why

Compose Manager, with `KINBOARD_*_DIR` under `/mnt/user/appdata/kinboard`.

## 5. Existing installs

### 5.1 The release that ships this: nothing changes

A git install updates as it always has (`git pull`, `./start.sh up`, or the
Diun self-update). What it gets:

| Part | What happens | Why nothing changes |
|---|---|---|
| `webapp/docker/docker-compose.yml` | unchanged | the new file is `compose.yml` at the root, which nothing on the git path reads. `start.sh` and the self-update pass `-f docker-compose.yml` explicitly (`start.sh:42`, `kinboard-self-update.sh:57`) |
| `.env` | untouched | `setup.sh` behaves as before. The init step does not run: the legacy file has no `init` service |
| `DATA_DIR` | unchanged; no `config/` appears | the same reason |
| the webapp image | new, as with every release | the entrypoint reads the environment first, and the legacy file sets every secret. The scheduler stays off (`KINBOARD_SCHEDULER` unset). The anon and service-role keys come from `.env`, as now |
| db, rest, go2rtc, cron, db-init | same definitions, so the same containers | `cron` is recreated after a new webapp, as on every release (`start.sh:217-230`) |
| `COMPOSE_FILES` overlays, Traefik, Diun | unchanged | none of them is touched |

Installs that run with overlays in `COMPOSE_FILES` and the Diun overlay,
including the maintainer's own, stay on this path until they choose otherwise.

### 5.2 Opting in later

For a git install that wants to become a one-file install. `./start.sh adopt`
can do steps 2–5 later; by hand:

1. **Take a backup** (Self-hosting → Backups) and note `DATA_DIR` from
   `webapp/docker/.env`.
2. **Stop the legacy stack**: `./start.sh down`. The containers go; the data
   stays. Both files use the same container names, so the new stack can't start
   while the old one runs.
3. **Write the new stack's `.env`** next to `compose.yml` (or into the UI's
   variables):
   - `KINBOARD_DB_DIR=$DATA_DIR/db`,
     `KINBOARD_STORAGE_DIR=$DATA_DIR/storage` and
     `KINBOARD_CONFIG_DIR=$DATA_DIR/config` (as absolute paths);
   - `WEBAPP_PORT`, `TZ` and `KINBOARD_TAG` as before;
   - **the existing secrets copied across**: `POSTGRES_PASSWORD`,
     `JWT_SECRET`, `CRON_SECRET`, `PRESENCE_SENSOR_TOKEN`, `VAPID_PUBLIC_KEY`
     and `VAPID_PRIVATE_KEY`. `ANON_KEY` and `SERVICE_ROLE_KEY` may come
     across too; they are equal to what the webapp would derive only if they
     were minted with the same payload, so keeping them is the safe choice.
4. **Up.** The init step writes each value into `config/secrets/` ("taken
   from .env"). The database opens with its existing password. Devices stay
   signed in: their sessions are random tokens in the database
   (`src/lib/session.ts:69`), not JWTs. Push keeps working, because the VAPID
   keys are the same.
5. **Check**: the version in Settings, a join from a new device, a test push.
   Afterwards the secret lines may stay in `.env` (they win, §4.1) or be
   removed (the files hold them).

**Not yet for:**

- **The Diun self-update.** It assumes the git layout (§4.8). Installs that
  use it stay on `docker-compose.yml` until the self-update learns
  `compose.yml` (PR 10).
- **Traefik.** Works: the overlay applies to `compose.yml` unchanged (§4.9).
- **Other `COMPOSE_FILES` overlays.** Most name `webapp`, `db` or the network
  and apply as they are. Any that mounts `./go2rtc.yaml` or `./init.sql` by
  relative path needs the file next to `compose.yml`.

## 6. Security

### 6.1 Where secrets live

In the `kinboard-config` volume under `secrets/`. By default that is a Docker
named volume, inside Docker's own directory, readable by root only. It is
mounted:

- **read-write** only into `init`;
- **read-only** into `db`, `db-init`, `rest` and `webapp`;
- **not at all** into go2rtc, which has no volume any more.

### 6.2 Permissions

The directory is `0750 root:0` and the files `0640 root:0`. Why not tighter:

| Reader | Runs as | Needs | Verified |
|---|---|---|---|
| PostgreSQL entrypoint | root, then drops to `postgres` | read at first start | `0600 root:root` works |
| PostgREST | uid 1000, gid 0 (the image sets `User: 1000` and nothing else) | read `jwt_secret` and `db_uri` | `0640 root:root` and `0644` work; **`0600 root:root` fails**: `FatalError … withBinaryFile: permission denied`, exit 1 |
| webapp entrypoint, db-init | root | read | — |

Group 0 is the narrowest set that includes PostgREST. On the host, uid 1000 is
usually the first human account. Owning the files by 1000 would hand them to
that account; group 0 normally holds only root.

### 6.3 A world-readable share

If the household points `KINBOARD_CONFIG_DIR` at a share that ignores `chmod`
(some SMB/NFS mounts, some FUSE layers), the files end up readable by whoever
can read the share. The init step reads the modes back and logs a warning
naming the files (§4.1 step 4). It doesn't refuse. The database directory on
the same share is just as readable, and anyone who can read it can read every
family's data directly. The secrets add the ability to mint tokens for the API,
which needs network access to the stack.

The named-volume default avoids the question. The Compose UIs page says that
whoever can read the data folder can read everything.

Compared with today, this is an improvement on three counts:

- **`.env` mode.** `setup.sh` creates `.env` by copying `.env.example`
  (`setup.sh:80`) and never narrows its mode. On the development machine it is
  `0664`.
- **`docker inspect`.** Every secret sits in container environments
  (`docker-compose.yml:279-342`), which `docker inspect` prints and Portainer
  shows on its container page. Files don't show there.
- **`db_uri`.** It replaces a connection string that carries the password in
  PostgREST's environment.

### 6.4 Rotation

Delete the file and restart. The init step generates a new value.

| Secret | What a new value costs |
|---|---|
| `jwt_secret` | nothing lasting. Family tokens are re-minted from the device session; signed file links expire anyway (`src/lib/files/signed.ts`) |
| `cron_secret` | nothing; only the scheduler uses it |
| `presence_sensor_token` | the sensor must be given the new token (Settings, §4.4) |
| `vapid_*` | every device's push subscription stops working. PR 6 has the webapp record the public key's fingerprint in `instance_settings`; on a mismatch it logs it, and Settings says "notifications were reset; enable them again on each device" |
| `postgres_password` | **never by deleting**. The init step refuses (§4.1 step 3). A documented procedure: `ALTER ROLE` for `postgres`, `supabase_admin` and `authenticator`, then write the file |

### 6.5 Backups

A complete backup is now three things: the database, the uploaded files and
`config/`. Without `config/`, a restore of the database **directory** can't
start: the init step refuses, because the cluster exists and its password file
doesn't. That is deliberate, and the message says what is missing. A restore
from a **dump** into a new install works with new secrets, except for push,
because the VAPID keys are new (§6.4).

What exists today:

- **The self-update's pre-upgrade backup** dumps the database and tars only
  `storage` (`kinboard-self-update.sh:171-173`). It gains `config/` when that
  directory exists, as a third archive with mode `0600`. For git installs that
  have no `config/`, nothing changes.
- **The documented manual backup** (`Self-hosting.md:204-302`) gets the same
  third step. Restoring needs `config/` in place before the first Up.
- **The in-app export** (`/api/export`) is a family's data. It leaves out
  `integration_secrets` and `oauth_credentials` by design
  (`src/app/api/export/route.ts:31-34`), and the files and secrets entirely.
  It is not a backup of the install and stays that way.
- **No `kinboard-backup` tool exists in this repo.** The name appears only as a
  test rig's data folder (`test-backup-restore.sh:50`) and an export filename.

A one-file household without a terminal has no backup path except its UI's
volume tools. A full backup downloadable from Settings is the real answer, and
big enough for its own RFC (§3, §11.10).

### 6.6 The Docker socket

Today's default stack gives ofelia the socket (`docker-compose.yml:366`). A
`:ro` mount doesn't make the API read-only: whoever holds the socket controls
the host. `compose.yml` has no container with the socket. Diun, when a
household adds it, gets it read-only for label and digest reads, or no socket
at all with the file provider (§4.7).

## 7. Failure modes

| What | What happens | What the household sees |
|---|---|---|
| The init step fails (unwritable volume, disk full, a refused filesystem) | exits non-zero; `db` never starts (`service_completed_successfully`) | Compose: "service init didn't complete successfully". The UI shows `init` exited with an error, and its log names the cause |
| Data on the Unraid flash drive (a relative path) | refused: `vfat` | the init log: "PostgreSQL can't keep its data on a FAT filesystem (a USB flash drive?). Set KINBOARD_DB_DIR to a folder under /mnt/user/appdata" |
| Data in a folder that's gone after a reboot (`tmpfs`, as CasaOS's temporary folder would be) | refused | the same, naming `tmpfs` |
| Some secrets missing (an interrupted first start, a hand-deleted file) | the missing ones are generated, except `postgres_password` with an existing cluster: refused | one log line per secret. For VAPID, the Settings notice (§6.4) |
| `.env` and the file disagree on `postgres_password` | refused, naming both | the log says which to remove |
| `.env` and the file disagree on another secret | `.env` wins; the old file kept as `.previous-<timestamp>` | a warning in the init log |
| A restored data directory, with `config/` | nothing generated; everything matches | nothing |
| A restored data directory, without `config/` | refused (the cluster exists, its password file doesn't) | the log says to restore `config/secrets/` or set `POSTGRES_PASSWORD` |
| A dump restored into a new install | works; new secrets | push must be enabled again on each device |
| Two stacks on one host with the same data | the second fails on the container name (`kinboard-db` is already in use) before it starts anything | the UI shows the name conflict |
| Two hosts sharing a data folder over the network | **not detected**. Two PostgreSQL servers on one directory corrupt it, and inside containers PostgreSQL's own `postmaster.pid` check can be fooled, because both sides see small, matching PIDs | the Compose UIs page says: never |
| `db-init` can't apply `init.sql` to an empty database | rolled back (`--single-transaction`); exits non-zero; `rest` and `webapp` wait | the db-init log shows the SQL error. The next Up retries on a still-empty schema |
| An image needs a newer `compose.yml` | it runs. Settings says so (§4.6) | the notice, with a link |

## 9. Steps and PRs

Each PR can ship alone and changes nothing for an install that doesn't use
what it adds.

## 10. Risks

- **Two compose files to keep in step.** The legacy file stays for git
  installs. The parity test covers the jobs. The images, healthchecks and
  environment of the shared services need the same kind of test, or the files
  drift the way the overlays once did.
- **The UIs are moving targets.** The table in §4.6 is from their source
  today. CasaOS especially is inferred, not tried.
- **Named volumes hide the data** from households that back up a share folder.
  The Compose UIs page leads with "where is my data", and setting a folder is
  one variable.
- **The internal scheduler is new code** for something ofelia has done
  reliably. It is small, the job routes don't change, and the parity test and
  rehearsal A watch it, but it is the largest new piece here.
- **`--single-transaction` around `init.sql`** is unverified (§4.2). If
  `pg_cron` or the publication refuses it, `db-init` needs a cleanup instead:
  drop the half-made schema on failure.

## 11. Open questions for the owner

1. **The scheduler.**
   - a. Move the jobs into the image for `compose.yml` (proposed), or keep
     ofelia with labels and accept that pasted files miss new jobs until
     re-pasted?
   - b. Keep the fixed-time jobs at UTC as ofelia runs them today (proposed,
     for parity), or move them to the household's zone?
2. **The default data location**: named volumes (proposed), or `./data` as
   today, which works in OMV, Dockge and a terminal but lands on the flash
   drive in Unraid and in a non-obvious place in Portainer?
3. **Automatic updates for one-file installs.** Publish the webhook image as
   `kinboard-updater` and give it an image-only mode, or stay with the notice,
   Diun notifications and Pull + Up (proposed for this RFC)?
4. **API keys per family** (proposed) **or per install** (`instance_settings`)?
5. **Where `compose.yml` lives**: the repo root plus a release asset
   (proposed), or only the release asset?
6. **When does `webapp/docker/docker-compose.yml` retire**, if ever? Not
   proposed here; the parity tests are the price of keeping it.
7. **Should the self-update's backup also copy `.env`?** Today a disk loss
   takes both. It is a change for existing installs, so not proposed.
8. **CasaOS**: support it, with literals instead of variables, or list it as
   "should work, not supported" until rehearsed on a real box?
9. **Unraid**: a Compose Manager page now (proposed). The CA template and the
   other stores are decided in [RFC-024](024-all-in-one-and-stores.md).
10. **A full backup downloadable from Settings**: worth an RFC of its own?

## 12. Not in this RFC

Changing how secrets are stored in the database (they stay plain text,
service-role only). Running without Docker. Kubernetes. Multiple webapp
replicas. Changes to the Traefik overlay beyond documenting it for
`compose.yml`. Retiring `start.sh`, `setup.sh` or the legacy compose file.
