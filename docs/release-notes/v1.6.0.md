# Kinboard 1.6.0

> **Read this before you upgrade.** Every device will be signed out, and the
> code needed to sign back in lives on a screen you cannot reach once that has
> happened. Write it down first: **Settings → Family → join code.**
>
> If you have already upgraded and are locked out, see
> [Recovering a lost join code](../../UPGRADING.md#recovering-a-lost-join-code).

This release closes a serious hole. If you have ever made your Kinboard
reachable from outside your home network — a domain, a reverse proxy, a
port forward — please treat everything in it as having been readable by
anyone who found the address, and read [What was exposed](#what-was-exposed).

---

## Why every device has to re-join

Kinboard's browser client talks to the database's API directly. Until now the
database trusted every request and relied on the app to ask only for its own
household's rows. That works while the app is the only thing making requests.
It stops working the moment anyone else can reach the API, because the key the
browser uses is public — it ships inside the page, as it must.

From 1.6.0 the database enforces the boundary itself. A device joins with the
family code and receives a session the browser cannot read or forge; every
query carries proof of which household it belongs to, and the database refuses
anything else.

The old sign-in state was not a credential — it was a note the browser wrote to
itself. It is not carried over, deliberately: accepting it would mean accepting
whatever any browser chose to write. Hence the re-join.

**Do the wall display or kiosk first**, since it is the one that needs someone
standing in front of it. Phones and laptops can be done whenever you next pick
them up; they will sit on the join screen until then, and nothing is lost.

## What was exposed

On a published instance, before this release, an unauthenticated request from
anywhere on the internet could read and write every table — including the one
holding join codes. We confirmed this against a live instance: a single request
returned a household's name and its join code.

Anyone holding a join code can add a device to that household.

If your Kinboard has been reachable from outside your network, we would
suggest, after upgrading:

- **rotate your join code** (Settings → Family), which invalidates any copy
  someone else obtained;
- **reconnect the integrations that hold credentials** — Home Assistant,
  Immich, Google Calendar, Unsplash — if you connected them before 1.6.0. Their
  tokens were moved out of general storage in an earlier 1.6.0 release, but
  rotating them costs little and removes the question.

A LAN-only instance was never reachable from outside, and the risk there was
limited to devices on your own network.

## Also in this release

Around ninety fixes. The ones most likely to affect you day to day:

- **The shopping list app** stops dropping you into the main dashboard, and now
  has a permanent button rather than only appearing in a tip you can dismiss
  forever.
- **The screensaver** stops showing the same photos. It picked each next photo
  at random, so one came back roughly every five minutes while some of the
  photos it had fetched were never shown at all.
- **Pocket money interest** below one cent a day is no longer discarded. At the
  default rate that meant any balance under €36.50 earned nothing, ever, while
  the settings screen advertised a rate.
- **The to-do badge** in the navigation stops sticking. Recurring chores are
  never marked complete, so it counted them forever.
- **Editing can clear a field.** Deleting a recipe's description, photo or prep
  time, or an event's location, used to report success and keep the old value.
- **Notifications** no longer switch themselves off on every device at once,
  and no longer fire for appointments you cancelled or moved.
- **Watchlist search works again** — every search returned an error, so nothing
  could be added at all.

See the [changelog](../../CHANGELOG.md) for the full list.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

Database migrations apply on boot; there is nothing to run by hand.

If you maintain your own compose file rather than using the bundled one, add
`JWT_SECRET` to the **webapp** service — it signs the tokens the browser uses,
and must match the one the database API verifies with:

```yaml
  webapp:
    environment:
      JWT_SECRET: ${JWT_SECRET}
```

Without it, joining still works but no data loads.

## Checking it worked

From a machine outside your network, with your public address:

```bash
curl -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY" \
  "https://your-kinboard.example/rest/v1/families?select=id,name,join_code"
```

An upgraded instance returns `[]`. Anything else means the migration did not
apply — check the webapp container's logs from boot, and see
[UPGRADING.md](../../UPGRADING.md).

## If it goes wrong

[UPGRADING.md](../../UPGRADING.md) has the rollback. It restores service
immediately and restores the exposure with it, so treat it as a way to buy
time rather than somewhere to stay — and do not leave a published instance in
that state.
