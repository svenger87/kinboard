# Kinboard 1.6.0

**Kinboard is now safe to reach from outside your home network.** The database
enforces household isolation itself, rather than trusting every request to ask
only for its own data. That is the release in one line, and it is the one that
makes a domain, a reverse proxy or a VPN-free setup a reasonable thing to want.

Alongside it: around ninety fixes from a full pass over the project.

> **One thing to do first.** Upgrading signs every device out, and the code to
> sign back in is on a screen you cannot reach once that has happened.
> **Write it down before you pull: Settings → Family → join code.**
>
> Already upgraded and locked out? The code is one command away —
> [recovering a lost join code](../../UPGRADING.md#recovering-a-lost-join-code).

---

## What changed

Kinboard's browser client talks to the database's API directly, which is what
makes it quick. Until now the database accepted whatever it was asked for and
relied on the app to only ask for its own household's rows. That is fine while
the app is the only thing making requests, and it stops being fine the moment
anything else can reach the API — because the key the browser uses is public.
It ships inside the page, as it has to.

From 1.6.0, row-level security in Postgres enforces the boundary. A device
joins with the family code and receives a session the browser cannot read or
forge; every query carries proof of which household it belongs to, and the
database refuses anything else.

**Why that means re-joining.** The old sign-in state was a note the browser
wrote to itself, not a credential the server had issued. Carrying it over would
mean trusting whatever a browser chose to write, so 1.6.0 issues a real one
instead — and that means signing in again, once, per device.

Do the wall display or kiosk first, since it is the one that needs someone
standing in front of it. Phones and laptops can wait until you next pick them
up; they will sit on the join screen, and nothing is lost.

## If your instance has been reachable from the internet

Before 1.6.0, a published instance was readable by anyone who found the
address — including the join code, and anyone with a join code can add a
device. We would suggest, once you have upgraded:

- **rotate your join code** (Settings → Family), which invalidates any copy
  that got out;
- **reconnect Home Assistant, Immich, Google Calendar or Unsplash** if you
  connected them before 1.6.0. Their tokens were moved into protected storage
  earlier in the 1.6.0 series, so this is belt-and-braces rather than urgent.

A LAN-only instance was never reachable from outside, and the exposure there
was limited to devices already on your network.

## Also in this release

The ones you are most likely to notice:

- **The shopping list app** stops dropping you into the main dashboard, and has
  a permanent button instead of only appearing in a tip you can dismiss for
  good.
- **The screensaver** stops repeating itself. It picked each photo at random,
  so one came back every few minutes while others it had fetched were never
  shown at all.
- **Pocket money interest** below a cent a day is no longer discarded. At the
  default rate that meant balances under €36.50 earned nothing, ever, while the
  settings screen advertised a rate.
- **The to-do badge** stops sticking. Recurring chores are never marked
  complete, so it counted them forever.
- **Editing can clear a field.** Deleting a recipe's description, photo or prep
  time, or an event's location, used to report success and keep the old value.
- **Notifications** no longer switch themselves off across every device at
  once, and no longer fire for appointments you cancelled or moved.
- **Watchlist search works** — every search used to fail, so nothing could be
  added at all.

The [changelog](../../CHANGELOG.md) has the full list.

## Upgrading

```bash
docker compose pull && docker compose up -d
```

Database migrations apply on boot; there is nothing to run by hand.

If you maintain your own compose file rather than using the bundled one, add
`JWT_SECRET` to the **webapp** service — it signs the tokens the browser uses,
and must match the one the database API verifies with:

```yaml
  webapp:
    environment:
      JWT_SECRET: ${JWT_SECRET}
```

Without it you can join, but nothing loads.

## Checking it worked

From a machine outside your network:

```bash
curl -H "apikey: $ANON_KEY" -H "Authorization: Bearer $ANON_KEY" \
  "https://your-kinboard.example/rest/v1/families?select=id,name,join_code"
```

An upgraded instance returns `[]`. Anything else means the migration did not
apply — check the webapp container's logs from boot, and see
[UPGRADING.md](../../UPGRADING.md).

## If it goes wrong

[UPGRADING.md](../../UPGRADING.md) has a rollback. It restores service
immediately and restores the old exposure with it, so treat it as a way to buy
time rather than somewhere to stay — and do not leave a published instance in
that state.
